# Bootstrapping a new cluster

Work through this in order on a cluster you have not used before. Each step ends by writing what you learned into the project's agent file, which is what makes the next session cheap. Nothing here is specific to one cluster.

## 0. Ask for what you cannot discover

Before anything else, collect the facts in "Facts you must be given" in `SKILL.md`: the directory on the shared filesystem that is yours, the account, the partition for this work, registry credentials, the model and its token, and the path of any image or model cache that already exists.

Ask for all of them in one message. A setup built on a guessed path looks fine until it fails somewhere far from the cause.

## 1. Discover

Run the probes in `SKILL.md`, and add these two.

```bash
grep lustre /proc/mounts        # or the parallel filesystem in use
```

Look for `flock` against `localflock` or neither. With real `flock`, the locks that cargo and uv take on a shared cache hold across nodes, so two jobs on different nodes can share one cache directory. With `localflock` they do not, and a shared cache races. Mount options can differ between a login node and a compute node, so run this in a job as well.

```bash
scontrol show partition <name> | grep -oE 'OverSubscribe=[A-Z]+|PriorityTier=[0-9]+|PreemptMode=[A-Z,]+'
```

Write down: the architecture of each node class, whether `$HOME` exists on a compute node, the node-local scratch path and its size, the GPU request syntax the partitions accept, which partition is the preemptible tier, the topology flag for a multi-node run, the job-name policy, and the lock mode.

## 2. Credentials

Registry credentials for the container runtime, at the path it expects, mode 600. Render them from the secret store rather than copying a file between clusters. Where compute nodes have no `$HOME`, plan to stage them per node.

## 3. Toolchain: prefer the image's

Before building a farm of host-side tools, list what the image already carries.

```bash
unsquashfs -l <image>.sqsh | grep -E 'bin/protoc$|libclang|bin/uv$|bin/cargo$'
```

A development image usually ships the compiler, the protobuf compiler, libclang, and the Python and Rust tooling. An environment variable that points at a host-side copy will override the image's, so set one only where the image lacks the tool. Make each such variable conditional on the file being absent, not unconditional, or a correct image gets bypassed.

Only a bare run, outside the container, needs the host-side farm. Decide whether you need bare runs at all before building one.

## 4. Per-worktree environment

The environment file that makes a build work must be tracked, or generated by a tracked script. An untracked file in one checkout cannot reach a second worktree, an agent's worktree, or a second cluster, and it is the single point of failure most likely to be discovered at the worst time.

Keep the cluster's root path in one place that the file reads, rather than writing absolute paths into it. Where the repository is public, the generator belongs in it and the paths do not.

Give each worktree its own target directory, under each architecture. A target directory shared between two checkouts makes each one invalidate the other's fingerprints, and the cost looks like a slow compiler rather than a configuration mistake.

## 5. Images

Import a base image for the compute architecture, and run any bake step, following the container rules in `SKILL.md`. An image is a large file: copying one between clusters is usually faster than importing it again, where both can see the same storage.

## 6. Caches and large data

Create the cache directories on the parallel filesystem and point the tools at them: the package manager, the compiler's target directory, the interpreter, and the model cache. Re-downloading a model cache can take far longer than every other step combined, so start it first and let it run.

## 7. Re-home anything keyed by path

An agent's memory, a tool's state directory, and anything else addressed by the absolute path of the work tree will not load under a different root. Find those and move them before you conclude the setup works.

## 8. Record

Write the facts from step 1 into the project's agent file, next to the commands that use them. A fact discovered and not written down is a fact the next session pays for again.
